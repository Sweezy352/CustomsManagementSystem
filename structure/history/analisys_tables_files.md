Логика загрузки документов, описанная в `customs_backend_architecture.md`, использует правильную и масштабируемую архитектуру.

### Основная идея: Разделение "физического файла" и его "логического смысла"

Процесс разделен на два независимых компонента:

1.  **`FileStorage`**: Это "цифровой склад" или "файловый архив". Его единственная задача — принять любой файл, сохранить его в надежном месте (на диске, в S3, MinIO) и присвоить ему уникальный ID. Эта таблица ничего не знает о том, *что это за документ* (паспорт, инвойс или сертификат). Она просто хранит файлы.

2.  **`CompanyDocument` / `DeclarationDocument`**: Это "таблицы-связки" или "карточки учета". Они не хранят сами файлы. Их задача — придать файлу из `FileStorage` **контекст и смысл**. Они отвечают на вопросы:
    *   К какой компании или декларации относится этот файл? (`company_id`, `declaration_id`)
    *   Что это за документ по своей сути? (`document_type`, `type`)
    *   Проверен ли он? (`verified`, `verified_by`)

### Пошаговый процесс загрузки документа (на примере инвойса для декларации)

Представьте, что пользователь хочет прикрепить инвойс (файл `invoice.pdf`) к своей декларации №101.

**Шаг 1: Физическая загрузка файла на сервер.**

1.  Пользователь в интерфейсе нажимает "Загрузить документ" и выбирает `invoice.pdf`.
2.  Фронтенд отправляет этот файл на специальный, общий для всех загрузок, эндпоинт, например: `POST /api/files/upload`.
3.  Бэкенд получает файл:
    *   Сохраняет его в хранилище (например, в S3 по пути `s3://bucket/docs/a1b2-c3d4-e5f6.pdf`).
    *   Создает **одну запись** в таблице `FileStorage`.

**Запись в `FileStorage`:**

| id | original_name | mime_type | size | path | uploaded_by |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **550** | `invoice.pdf` | `application/pdf` | 123456 | `docs/a1b2-c3d4-e5f6.pdf` | 78 (ID юзера) |

4.  Бэкенд возвращает фронтенду ID этого файла: `{ "file_id": 550 }`.

**На этом этапе файл уже на сервере, но система еще не знает, что с ним делать.**

**Шаг 2: Логическое прикрепление файла к декларации.**

1.  Фронтенд, получив `file_id: 550`, немедленно делает второй запрос, но уже на другой, более конкретный эндпоинт: `POST /api/declarations/101/documents`.
2.  В теле этого запроса он передает ID файла и его тип:
    ```json
    {
      "file_id": 550,
      "document_type": "FIN_INVOICE"
    }
    ```
3.  Бэкенд получает этот запрос и создает **одну запись** в таблице `DeclarationDocument`.

**Запись в `DeclarationDocument`:**

| id | declaration_id | product_id | type | file_id |
| :--- | :--- | :--- | :--- | :--- |
| 9001 | 101 | NULL | `FIN_INVOICE` | **550** |

Теперь система знает, что файл с ID `550` из `FileStorage` является финансовым инвойсом для декларации №101.

### Преимущества такого подхода:

1.  **Нет дублирования:** Вся информация о файле (размер, имя, путь) хранится в одном месте. Таблицы-связки очень "легкие".
2.  **Гибкость:** Вы можете привязать один и тот же физический файл к разным сущностям, если это потребуется.
3.  **Разделение ответственности (Separation of Concerns):** У вас есть отдельный сервис или модуль, который отвечает только за хранение файлов, и он ничего не знает о бизнес-логике. Это упрощает разработку и тестирование.
4.  **Простота для проверок:** Инспектору для проверки документов декларации №101 нужно просто сделать запрос к таблице `DeclarationDocument` по `declaration_id = 101` и получить список всех привязанных `file_id`.

Эта архитектура является надежной и проверенной временем практикой для работы с файлами.
