# Анализ и рефакторинг архитектуры базы данных

Этот документ содержит ключевые решения и рекомендации, выработанные в ходе анализа первоначальной схемы базы данных.

---

## 1. Выбор типов данных

Правильный выбор типов данных критически важен для точности, производительности и безопасности.

| Поле | Рекомендуемый тип | Обоснование |
| :--- | :--- | :--- |
| **Коды (ТН ВЭД, ИНН)** | `VARCHAR(N)` | Это идентификаторы, а не числа. `VARCHAR` сохраняет ведущие нули и защищает от математических операций. |
| **Количество (`quantity`)** | `BIGINT` | Целое число. `BIGINT` выбран для защиты от переполнения при работе с большими партиями товаров. |
| **Вес (`weight`)** | `DECIMAL(10, 3)` | Гарантирует точность до грамма (до 9999 тонн). **Никогда не использовать `FLOAT`** из-за ошибок округления. |
| **Деньги и Ставки (%)** | `DECIMAL(19, 2)` / `DECIMAL(8, 4)` | Гарантирует абсолютную финансовую точность. `FLOAT` недопустим. |
| **Даты и время** | `TIMESTAMP WITH TIME ZONE` | Всегда хранить время с часовым поясом для избежания путаницы и корректной работы в разных регионах. |
| **MIME-тип файла** | `VARCHAR(255)` | Покрывает все стандартные и нестандартные MIME-типы. |
| **Размер файла (`size`)** | `BIGINT` | Хранит размер в байтах. `INTEGER` имеет ограничение в ~2 ГБ, что недостаточно для современных файлов. |
| **Путь к файлу (`path`)** | `VARCHAR(1024)` | Соответствует максимальной длине ключа объекта в S3/MinIO, обеспечивая совместимость. |

## 2. Логика хранения файлов

Разделение физического файла и его логического смысла — ключевой аспект архитектуры.

1.  **`file_storage`**: "Цифровой склад". Хранит сам файл (в MinIO/S3), его метаданные (`size`, `mime_type`) и уникальный путь (`path`). Ничего не знает о бизнес-логике.
2.  **Таблицы-связки** (`company_documents`, `declaration_documents`): Придают файлу контекст. Отвечают на вопросы "Что это за документ?" и "К чему он относится?". Хранят только ссылку (`file_id`) на запись в `file_storage`.

## 3. Справочники и историчность данных

### Таблица `tnved_codes`
Это не дублирование, а **единый источник правды**.
*   **Назначение:** Централизованный справочник кодов, их описаний и **стандартных ставок** (`standard_..._rate_percent`).
*   **Целостность:** Позволяет использовать внешний ключ в `declaration_products`, защищая от неверных кодов.
*   **Управление:** Администратор управляет ставками в одном месте. Первоначальное заполнение должно производиться **автоматически** через скрипт-сидер, а не вручную.

### Историчность ставок
*   **Проблема:** Если изменить ставку в `tnved_codes`, все старые декларации станут некорректными.
*   **Решение:** В таблицу `declaration_products` **необходимо добавить поля** для "заморозки" ставок на момент создания декларации (например, `vat_rate_applied`, `customs_duty_rate_applied`). При создании товара в декларации, значения копируются из `tnved_codes` в эти поля. Все последующие расчеты для этой декларации должны использовать **только эти "замороженные" значения**.

## 4. Роли и права доступа (RBAC)

Использование `varchar` для хранения роли в таблице `users` — негибкое решение.

*   **Проблема:** Нельзя назначить несколько ролей, сложно добавлять новые роли и управлять правами.
*   **Решение:** Внедрение **Role-Based Access Control (RBAC)** через три таблицы:
    1.  `users`: Хранит только данные пользователя.
    2.  `roles`: Справочник всех возможных ролей (`ADMIN`, `INSPECTOR`).
    3.  `user_roles`: Связующая таблица "многие-ко-многим" (`user_id`, `role_id`).
*   **Преимущества:** Гибкость, возможность назначения нескольких ролей, фундамент для детальной настройки прав доступа.

## 5. Система управления рисками

*   **`RiskRule`**: Таблица-конструктор, хранящая **правила** для оценки рисков.
*   **`condition_json` / `conditionExpression`**: Вместо парсинга сложного JSON, рекомендуется использовать **Spring Expression Language (SpEL)**. В поле хранится строка с выражением (например, `#product.pricePerUnit < 150`), которая выполняется движком SpEL. Это проще, мощнее и безопаснее.
*   **`DeclarationRisk`**: Таблица-журнал, хранящая **результат** применения правил к конкретной декларации (`HIGH`, `MEDIUM`, `LOW`).

## 6. Отчеты и кэширование

*   **Проблема:** Генерация отчетов "на лету" — очень ресурсоемкая операция.
*   **Решение:** Таблица `ReportCache` хранит **предварительно рассчитанные** агрегированные данные.
*   **Стратегия обновления:**
    *   **Инкрементальное обновление (по событию):** **Не рекомендуется.** Приводит к "гонке состояний", усложняет логику и создает тысячи мелких транзакций.
    *   **Пакетное обновление (по расписанию):** **Рекомендуемый подход.** Фоновая задача (`@Scheduled` в Spring) раз в час/день запускает один мощный агрегирующий запрос и полностью обновляет кэш. Это надежно, производительно и просто в поддержке.

---

## 7. Аудит и история

*   **`Declaration` vs `DeclarationHistory`**: Это не дублирование.
    *   `Declaration`: **Снимок текущего состояния.** Оптимизирован для быстрых запросов.
    *   `DeclarationHistory`: **Неизменяемый лог всех событий.** Отвечает на вопросы "Кто, что, когда и почему сделал?". Критически важен для аудита, разрешения споров и отладки.

---

## 8. Счета на оплату (Invoices)

*   **Проблема:** После одобрения декларации компании нужен официальный, детализированный документ для оплаты.
*   **Решение:** Создание двух таблиц:
    1.  **`payment_invoices` ("шапка"):** Хранит общую информацию — номер счета, итоговую сумму, статус (`ISSUED`, `PAID`), даты.
    2.  **`invoice_line_items` ("строки"):** Хранит **детализацию** итоговой суммы (например, "НДС на 'Смартфон'", "Пошлина на 'Чехлы'").
*   **Бизнес-процесс:** Счет создается **один раз и только после** одобрения декларации инспектором (`status = 'APPROVED'`). До этого момента система может показывать только предварительный расчет, не сохраняя его в базу.

## 9. Решение циклических зависимостей

*   **Проблема:** `users` ссылается на `companies`, а `companies` ссылается на `users`, что создает ошибку при создании таблиц.
*   **Решение:** Разорвать цикл на этапе миграции:
    1.  Создать таблицу `users` **без** внешнего ключа `company_id`.
    2.  Создать таблицу `companies` (она сможет сослаться на уже существующую `users`).
    3.  Использовать `ALTER TABLE users ADD FOREIGN KEY ...`, чтобы добавить недостающую связь.
